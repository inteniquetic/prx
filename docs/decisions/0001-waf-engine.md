# 0001 — WAF engine: เขียนเองใน tree

**สถานะ:** ตัดสินแล้ว (T504)
**วันที่วัด:** 2026-09-20
**สิ่งที่วัด:** OWASP CRS **v4.21.0** (commit `8d06076`, checkout ที่ tag)
**เครื่องมือ:** `spike/waf/` — reproduce ได้ ดู `spike/waf/README.md`

## ตัดสินอะไร

เขียน SecLang engine เองใน tree (ทางเลือก C ของ [`docs/PLUGIN-WAF-PLAN.md`](../PLUGIN-WAF-PLAN.md) §2)
โดย**ไม่**ใช้ libmodsecurity3 ผ่าน FFI เป็นตัวหลัก และ**ไม่**พึ่ง crate ของ proxy อื่น

เกณฑ์ที่ตั้งไว้**ก่อน**วัด (§3 ของแผน) คือ CRS ≥ 95% คอมไพล์ผ่าน → เขียนเอง
ผลที่ได้อยู่เหนือเกณฑ์ชัดเจน เกณฑ์ที่เขียนล่วงหน้าจึงทำงานของมันสำเร็จ

## ตัวเลขที่ตัดสิน

### 1. CRS เข้ากับ regex ของ Rust ได้แค่ไหน

จาก 678 `SecRule` มี **312 ข้อใช้ `@rx`**

| | ผ่าน | ไม่ผ่าน |
|---|---|---|
| ป้อนดิบ ๆ | 305 (**97.8%**) | 7 |
| หลังชั้นแปลง ~120 บรรทัด | 312 (**100%**) | 0 |

**สิ่งที่สำคัญกว่าเปอร์เซ็นต์: ไม่มีข้อไหนเลยที่ล้มเพราะ backreference หรือ lookaround**
ซึ่งเป็นสองอย่างที่ `regex` ทำไม่ได้โดยธรรมชาติ ทั้ง 7 ข้อล้มด้วยเหตุผลเดียวกันสองแบบ
ซึ่งเป็นเรื่อง "PCRE ผ่อนปรน / `regex` เข้มงวด" ล้วน ๆ:

- 6 ข้อ: `{` หรือ `}` ที่ไม่ได้เป็น counted repetition — PCRE อ่านเป็นตัวอักษรธรรมดา
- 1 ข้อ: escape ที่ไม่จำเป็นใน character class (`[^\&\|\!]`)

แยกตาม paranoia level: PL1 ล้ม 5, PL2 ล้ม 2, PL3/PL4 ล้ม 0

### 2. ทำไมถึงเป็นแบบนั้น — และทำไมมันจะไม่เปลี่ยน

ไม่ใช่โชค CRS **ห้ามไว้เป็นนโยบายที่เขียนไว้** ใน `CONTRIBUTING.md`:

> The OWASP CRS tries to be compatible with non-backtracking regular expression
> engines, such as RE2 (…) To ensure compatibility (…) the following operations
> are **not** permitted: positive lookahead, negative lookahead, positive
> lookbehind, negative lookbehind, named capture groups, backreferences,
> named backreferences, conditionals, recursive calls to capture groups,
> possessive quantifiers, atomic groups.

เหตุผลที่เขาให้คือ ReDoS — เหตุผลเดียวกับที่ `regex` ไม่มี backtracking ตั้งแต่แรก
`CHANGES.md` มีรายการ "make X RE2 compatible" ซ้ำ ๆ หลายรอบ แปลว่าเป็นข้อผูกพัน
ที่เขาดูแลอยู่จริง ไม่ใช่คำพูดลอย ๆ

`regex` ของ Rust อยู่ในตระกูลเดียวกับ RE2 **ความเข้ากันได้นี้จึงเป็นคุณสมบัติที่
CRS รักษาให้ ไม่ใช่สิ่งที่เราต้องลุ้นทุกเวอร์ชัน**

### 3. ชั้นแปลงเปลี่ยนความหมายไหม — ไม่

คอมไพล์ผ่านไม่เท่ากับความหมายเดิม จึงทดสอบเทียบ: pattern ที่คอมไพล์ผ่าน**ทั้งสองแบบ**
(305 ข้อ) ถูกรันทั้งรูปเดิมและรูปที่แปลงแล้วบน corpus เดียวกัน — payload โจมตีจริง
7,067 สตริงที่ดึงมาจากชุดทดสอบ regression ของ CRS เอง

**2,155,435 การเปรียบเทียบ · ไม่ตรงกัน 0 ครั้ง** และชั้นแปลงแตะ pattern จริง 86 ข้อ
จึงไม่ใช่การทดสอบที่ผ่านเพราะไม่ได้ทำอะไร

### 4. crate ที่มีอยู่แล้วทำได้แค่ไหน

โหลด CRS v4.21.0 ทั้งชุดเป็นก้อนเดียว (แบบที่ `Include` ส่งมาจริง):

| crate | rule ที่โหลดได้ | เวลาโหลด | ปัญหา | license |
|---|---|---|---|---|
| `zentinel-modsec` 0.4.0 | 685 | 236 ms | ไม่มี | Apache-2.0 |
| `barbacane-waf` 0.1.1 | 613 | 910 ms | ไม่รองรับ `@beginsWith` (1 ข้อ) | MIT OR Apache-2.0 |

ทั้งคู่ build ได้ ไม่ต้องพึ่ง C++ และเร็วพอ — **ทั้งคู่เป็นตัวเลือกที่ใช้ได้จริง ไม่ใช่ของเล่น**

`barbacane-waf` มีโมดูล `regex_compat` ที่ค้นพบ**เรื่องเดียวกันเป๊ะ**โดยอิสระ
(วัดบน CRS v4.9.0: 268/273 ผ่าน ที่เหลือเป็นสองเคสเดิม) และออกแบบดีกว่าที่ spike นี้ทำ:
เขาจะพยายามซ่อม**หลัง**จากคอมไพล์ตรง ๆ ไม่ผ่านเท่านั้น โดยให้เหตุผลว่า

> Rewriting an accepted pattern would be an unreviewed semantic change to a
> security control.

ถูกต้องกว่าที่ spike นี้ทำ (ซึ่งแปลงทุกอันแล้วพิสูจน์ทีหลังว่าไม่เปลี่ยนความหมาย)
**ข้อนี้ต้องยกมาใช้ใน T505**

### 5. libmodsecurity3 (ทางเลือก A)

`libmodsecurity3` ไม่มีในระบบและ **ไม่มีใน apt ของเครื่องนี้** (`Candidate: (none)`)
จึงวัดเทียบไม่ได้ในรอบนี้ — แต่ไม่กระทบการตัดสินใจ เพราะเหตุผลที่ไม่เอามันเป็นตัวหลัก
ไม่ใช่เรื่องความเร็ว (ดู §2 ของแผน: API เป็น synchronous ในเวิร์กเกอร์ async,
PCRE backtracking ไม่มี worst case, และเอา C++ ก้อนใหญ่มาวางบน data path ของตัวที่ทำ security)

มันยังอยู่ในฐานะ plugin หลัง feature flag สำหรับคนที่ต้องการ compat 100% วันนี้

## ทำไมเลือกเขียนเอง ทั้งที่มี crate ที่ใช้ได้

ข้อนี้เป็นการตัดสินใจ ไม่ใช่ข้อสรุปจากตัวเลข จึงเขียนเหตุผลไว้ให้เถียงได้:

1. **ความเสี่ยงทางเทคนิคที่กลัวกันหมดไปแล้ว** — เรื่องที่น่ากลัวคือ regex compatibility
   และมันจบแล้วที่ 100% พร้อมนโยบายของ CRS รองรับ ที่เหลือคืองานกว้างแต่ตื้น
   (operators, transformations, variables) ที่ทำทีละชิ้นได้ และมี regression suite
   ของ CRS เป็นตัวตัดสินถูกผิด
2. **ของที่อยู่บน data path ของ security control ไม่ควรเป็น 0.x ของ proxy คู่แข่ง** —
   ทั้งสอง crate เป็นส่วนหนึ่งของ product ที่แข่งกับ prx โดยตรง (zentinelproxy, parapet)
   การฝากคอขวดด้านความเร็วและ roadmap ไว้กับคนที่แข่งกับเราเป็นความเสี่ยงคนละแบบ
   กับความเสี่ยงทางเทคนิค และแก้ทีหลังยากกว่า
3. **ไม่ได้เลือกเพราะความเร็ว** — ตัวเลขข้างล่างบอกว่าความเร็วไม่ใช่ตัวแยก

**เงื่อนไขที่จะกลับมาทบทวน:** ถ้า T505–T506 ทำไปแล้วพบว่างาน operator/transformation
บานกว่าที่ประเมิน หรือถ้า crate ใดถึง 1.0 และแยกออกจาก proxy ต้นสังกัด
ให้เอา `barbacane-waf` (license MIT/Apache เอื้อต่อการ vendor) มาพิจารณาใหม่
โดยไม่ต้องรู้สึกว่าเป็นการถอย

## สิ่งที่วัดแล้วขัดกับแผน — แผนต้องแก้

วัด 312 pattern ต่อ 7,067 payload บน release build ผลทั้งสามวิธีตรงกันหมด
(107,434 hit เท่ากันทุกวิธี) แต่ความเร็วไม่เป็นไปตามที่แผนเขียนไว้:

| วิธี | µs ต่อ request | เทียบ naive |
|---|---|---|
| วนรันทั้ง 312 ข้อ (naive) | **82** | 1× |
| aho-corasick prefilter แล้วค่อยรัน | **42** | เร็วขึ้น 2× |
| `RegexSet` ทั้งชุด | **1,503** | **ช้าลง 18×** |

สามข้อที่ต้องแก้ในแผน:

1. **`RegexSet` ต่อ target เป็นความคิดที่ผิด** — แผน §5 ข้อ 2 เสนอไว้ วัดแล้วช้ากว่า
   naive 18 เท่า และ `RegexSet` ของ CRS ทั้งชุดยัง**ไม่ผ่าน size limit 10 MB
   ที่เป็นค่าเริ่มต้นของ crate** ด้วย ต้องถอดข้อเสนอนี้ออก
2. **prefilter ช่วยจริงแต่ 2× ไม่ใช่ "O(rules) → O(1)"** อย่างที่แผนเขียน —
   ข้ามการรัน regex ได้ 34.8% เพราะมีแค่ 110 จาก 312 pattern ที่ดึง literal
   ที่ใช้กรองได้ อีก 202 ข้อต้องรันทุกครั้ง (CRS ขึ้นต้นด้วย `(?i)` และ alternation กันเยอะ)
3. **naive เร็วพออยู่แล้ว** — 82 µs/request เทียบกับ budget 1 ms ที่แผนตั้งไว้
   แปลว่างาน optimize ใน T508 เร่งด่วนน้อยกว่าที่แผนทำให้รู้สึก

**ข้อจำกัดของตัวเลขชุดนี้ที่ต้องพูดให้ชัด:** วัดการรันทุก pattern กับ **สตริงเดียว**
ต่อ request แต่ WAF จริงรันแต่ละกฎกับ**ตัวแปรหลายสิบตัว** (ARGS, headers, cookies, body)
ต้นทุนจริงจึงราว 82 µs × จำนวนตัวแปร ซึ่งอาจดันเข้าไปอยู่ระดับ ms ได้
budget ใน T508 ยังต้องมี และยังต้องวัดใหม่ตอนมี variable extraction จริง

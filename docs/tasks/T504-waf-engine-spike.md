# T504 — Spike: วัด CRS compat แล้วเลือก engine

**Phase:** 5 · Plugin & WAF
**Status:** ✅ done
**Size:** M (~1d)
**Depends on:** — (ไม่พึ่งอะไรเลย · spike นี้อยู่นอกโค้ดเบสของ prx ทั้งหมด)
**Files:** `docs/decisions/0001-waf-engine.md`, `spike/waf/`, `docs/PLUGIN-WAF-PLAN.md`

> **ทำได้ทันที** — งานนี้แค่โหลด CRS มานับและ benchmark crate ไม่แตะ request path
> จึงเป็นใบที่ควรหยิบก่อนใครในเฟสนี้ไม่ว่าจะตัดสินใจเรื่อง plugin อย่างไร

## เป้าหมาย

ได้ตัวเลขมาตัดสินว่าจะเขียน SecLang engine เอง ใช้ crate ที่มีอยู่ หรือพลิกไป proxy-wasm
**ก่อน**ที่จะมีใครเขียน parser สักบรรทัด

## สถานะปัจจุบัน

เลือกไว้แล้วว่า rule format คือ SecLang/SecRules เพื่อให้ OWASP CRS ใช้ได้
แต่ "compatible" เป็นสเปกตรัม และยังไม่มีใครรู้ว่า prx จะไปถึงจุดไหนของสเปกตรัมนั้นได้

ข้อจำกัดที่ทำให้ต้องวัด: `regex` ของ Rust ไม่รองรับ backreference และ lookaround
เพราะนั่นคือราคาของการรับประกัน linear time (ซึ่งกับ WAF คือฟีเจอร์ ไม่ใช่ข้อจำกัด — WAF
ที่ถูก DoS ด้วย ReDoS คือช่องโหว่)

## ขอบเขตงาน

1. **ตัวเลขหลัก** — ดาวน์โหลด OWASP CRS ฉบับปัจจุบัน ดึง regex จากทุก `SecRule` แล้วนับว่า
   คอมไพล์ผ่าน `regex` ได้กี่ % · กฎที่ไม่ผ่านต้องจำแนกด้วยว่าเพราะอะไร (backreference,
   lookahead, possessive, syntax อื่น) และกฎพวกนั้นอยู่ใน paranoia level ไหน
   — กฎที่พังทั้งหมดอยู่ที่ PL4 มีความหมายต่างจากพังที่ PL1 มาก
2. **เทียบสี่ทางด้วยของจริง ไม่ใช่ด้วย README:**
   - เขียนเอง (prototype เล็ก ๆ ที่รันได้แค่ `@rx` + `@pm` พอให้วัด)
   - [`zentinel-modsec`](https://crates.io/crates/zentinel-modsec) 0.4.0
   - [`barbacane-waf`](https://crates.io/crates/barbacane-waf) 0.1.1
   - [`modsecurity`](https://crates.io/crates/modsecurity) (FFI → libmodsecurity3)
   วัด: กฎที่โหลดได้, เวลา/ความจำตอนโหลด CRS, latency ต่อ request, RSS, และ
   **ผลตรวจจับบน corpus เดียวกัน** (ตัวไหนบล็อกอะไรได้/ไม่ได้)
3. **ตรวจสถานะจริงของ upstream** — libmodsecurity3 ยังถูกดูแลอยู่แค่ไหน, CRS เวอร์ชันล่าสุดคืออะไร,
   สองcrate ฝั่ง pure-Rust มี commit ล่าสุดเมื่อไหร่และ test ครอบแค่ไหน
   **ห้ามเชื่อบรรทัดใน `PLUGIN-WAF-PLAN.md` ข้อนี้** — มันเขียนจากข้อมูลที่อาจเก่าแล้ว
4. **License และการพึ่งพา** — `zentinel-modsec` และ `barbacane-waf` เป็นส่วนหนึ่งของ proxy
   คู่แข่ง ถ้าจะใช้ต้องประเมินเรื่อง vendoring, license, และความเสี่ยงที่ upstream จะเปลี่ยนทิศ
5. **เขียน decision record** ที่ `docs/decisions/0001-waf-engine.md` — ตัวเลข, ทางที่เลือก,
   ทางที่ไม่เลือกพร้อมเหตุผล, และเงื่อนไขที่จะทำให้กลับมาทบทวนใหม่

## เกณฑ์ตัดสิน (ตั้งไว้ก่อนวัด เพื่อไม่ให้ตัวเลขถูกตีความเข้าข้างคำตอบที่อยากได้)

| CRS ที่คอมไพล์ผ่าน | ทางที่เลือก |
|---|---|
| ≥ 95% | เขียนเอง (T505–T508) · กฎที่เหลือ skip แบบดังตามกติกาข้อ 5 ของแผน |
| 80–95% | เขียนเอง + fallback engine สำหรับกฎที่เหลือ (ขอบเขตเพิ่ม ~1 task) |
| < 80% | พลิกไป T510 (proxy-wasm) แล้วรัน `coraza-proxy-wasm` |

ถ้า crate ฝั่ง pure-Rust ตัวใดตัวหนึ่งชนะทั้ง compat และ perf อย่างชัดเจน **ให้ใช้มัน** —
การเขียนเองไม่ใช่เป้าหมาย การมี WAF ที่เร็วและถูกต้องต่างหากที่เป็น

## ผลลัพธ์

**ตัดสินแล้ว: เขียน SecLang engine เองใน tree** ตามเกณฑ์ ≥95% ที่ตั้งไว้ก่อนวัด
รายละเอียดทั้งหมดอยู่ใน [`docs/decisions/0001-waf-engine.md`](../decisions/0001-waf-engine.md)

ตัวเลขหลัก (CRS v4.21.0, 678 SecRule, 312 ข้อใช้ `@rx`):

| | |
|---|---|
| คอมไพล์ผ่านดิบ ๆ | **305/312 (97.8%)** |
| หลังชั้นแปลง ~120 บรรทัด | **312/312 (100%)** |
| ต้องใช้ backreference หรือ lookaround | **0** |
| differential test ของชั้นแปลง | 2,155,435 เปรียบเทียบ · ไม่ตรงกัน **0** |

**สิ่งที่สำคัญกว่าเปอร์เซ็นต์:** CRS ห้าม lookahead/lookbehind/backreference/
possessive quantifier/atomic group ไว้เป็น**นโยบายที่เขียนไว้ใน `CONTRIBUTING.md`**
เพื่อให้เข้ากับ engine ตระกูล RE2 โดยอ้างเหตุผลเรื่อง ReDoS — ความเข้ากันได้นี้จึงเป็น
คุณสมบัติที่ CRS รักษาให้ ไม่ใช่โชคที่ต้องลุ้นทุกเวอร์ชัน

## Acceptance criteria

- [x] มีตัวเลข % CRS compat พร้อมการจำแนกสาเหตุและแยกตาม paranoia level —
      97.8% → 100%; สาเหตุทั้งหมดเป็นสองเคส (`{}` ที่เป็นตัวอักษร, escape เกินใน class);
      PL1 ล้ม 5, PL2 ล้ม 2, PL3/PL4 ล้ม 0
- [x] benchmark บน corpus และ hardware เดียวกัน reproduce ได้ — `spike/waf/README.md`
      มีขั้นตอนครบ · **วัดได้ 3 จาก 4 ทาง**: pure-Rust สองตัวโหลด CRS ได้จริง
      (zentinel 685 rule/236 ms, barbacane 613 rule/910 ms) และ prototype ของเราเอง
      · **libmodsecurity3 วัดไม่ได้** เพราะไม่มีในระบบและไม่มีใน apt (`Candidate: (none)`)
      ซึ่งบันทึกไว้ตรง ๆ ว่าวัดไม่ได้ ไม่ใช่เดาแทน
- [x] มี `docs/decisions/0001-waf-engine.md` ที่ระบุทางเลือก เหตุผล และเงื่อนไขทบทวน
- [x] T505–T510 อัปเดตตามผล — T510 ไม่ต้องเป็นแผนสำรองของ WAF อีกแล้ว,
      T508 ต้องแก้แผนเพราะข้อเสนอเดิมสองข้อผิด

## สิ่งที่วัดแล้วขัดกับแผนของเราเอง

spike ทำงานของมันสำเร็จในทางที่ไม่ได้คาดไว้ — มันไม่ได้แค่ยืนยันแผน แต่**หักล้างสองข้อ**:

1. **`RegexSet` ต่อ target ผิด** — แผน §5 เสนอไว้ วัดแล้ว **ช้ากว่า naive 18 เท่า**
   (1,503 µs vs 82 µs ต่อ request) และ `RegexSet` ของ CRS ทั้งชุดยังไม่ผ่าน
   size limit 10 MB ที่เป็นค่าเริ่มต้นของ crate ด้วยซ้ำ — ถอดออกจากแผนแล้ว
2. **prefilter ช่วย 2× ไม่ใช่ "O(rules)→O(1)"** — ข้าม regex ได้ 34.8%
   เพราะมีแค่ 110/312 pattern ที่ดึง literal ใช้กรองได้
3. **naive เร็วพออยู่แล้ว** — 82 µs/request เทียบกับ budget 1 ms ที่แผนตั้งไว้
   งาน optimize ใน T508 จึงเร่งด่วนน้อยกว่าที่แผนทำให้รู้สึก

**ข้อจำกัดที่ต้องพูดให้ชัด:** ตัวเลขนี้วัดการรันทุก pattern กับ**สตริงเดียว**ต่อ request
แต่ WAF จริงรันแต่ละกฎกับ**ตัวแปรหลายสิบตัว** ต้นทุนจริงจึงราว 82 µs × จำนวนตัวแปร
budget ใน T508 ยังต้องมี และต้องวัดใหม่เมื่อมี variable extraction จริง

## วิธีทดสอบ

spike นี้ไม่ได้อยู่บน build ของ prx — ผลลัพธ์คือตัวเลขกับเอกสาร
แต่โค้ดถูกเก็บไว้ใน `spike/waf/` พร้อมวิธี reproduce เพราะการตัดสินใจที่ทำซ้ำไม่ได้
คือความเห็น ไม่ใช่การวัด

## Out of scope

- เขียน engine จริง — งานนี้แค่ prototype พอให้วัด
